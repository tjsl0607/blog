처음 RSC를 도입하자고 했을 때 팀의 반응은 반반이었습니다. 서버와 클라이언트의 경계가 흐려진다는 게 오히려 복잡도를 높일 거라는 의견도 있었죠. 3개월이 지난 지금, 좋았던 점과 아쉬웠던 점을 정리해 봅니다.

## 데이터 패칭이 단순해졌다

가장 크게 체감한 변화는 `useEffect` 안에서 데이터를 불러오던 코드가 거의 사라졌다는 점입니다. 로딩 상태와 에러 상태를 컴포넌트마다 따로 관리할 필요가 없어졌어요.

```tsx
// app/posts/page.tsx
export default async function Page() {
  const posts = await getPosts();
  return <PostList posts={posts} />;
}
```

### 워터폴은 여전히 주의해야 한다

다만 `await`를 순서대로 늘어놓으면 요청이 직렬로 실행됩니다. 서로 의존하지 않는 요청은 `Promise.all`로 묶어야 해요.

```ts
const [user, posts] = await Promise.all([getUser(id), getPosts(id)]);
```

## 경계를 긋는 습관

> 결국 중요한 건 어떤 컴포넌트가 상호작용을 필요로 하는지 명확히 구분하는 습관이었습니다.

`'use client'`를 최대한 잎사귀(leaf) 컴포넌트 쪽으로 밀어내면 번들 크기가 눈에 띄게 줄어듭니다. 우리 팀은 아래 기준을 정해서 쓰고 있어요.

- 상태나 이벤트 핸들러가 필요하면 클라이언트 컴포넌트
- 브라우저 API를 쓰면 클라이언트 컴포넌트
- 그 외에는 전부 서버 컴포넌트

## 아쉬웠던 점

캐싱 동작을 예측하기 어려운 순간이 꽤 있었습니다. 특히 개발 환경과 프로덕션의 동작 차이 때문에 한참 헤맨 적이 있는데, 이건 따로 글로 정리해 보려고 합니다.

## 마치며

러닝 커브는 분명히 있지만, 한 번 익숙해지면 되돌아가기 어렵다는 게 팀의 공통된 의견입니다.
